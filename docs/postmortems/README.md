# 故障演练与 Postmortem

## 为什么要有这个目录

简历上写「熟悉 Kubernetes 运维」很容易，但面试官一问「你遇到过什么故障、怎么定位的、
后来改了什么」就露馅了。**这个目录就是那份答案。**

一份好的 Postmortem 要能回答四件事：

1. **现象**：用户/监控看到了什么（要有截图级的具体信息，比如报错原文）
2. **根因**：为什么会这样（要挖到机制层，不能停在「重启就好了」）
3. **证据**：怎么证明根因判断是对的（指标、日志、命令输出）
4. **改进**：以后怎么防止 / 更快发现（要具体到可执行的动作，不能写「加强监控」）

## 写作原则

- **对事不对人**：写成「流程缺了一环」，而不是「谁操作失误」。写清楚了下次才有人敢如实上报。
- **保留原始输出**：报错原文、命令输出不要「美化」，那是证据。
- **区分「演练」和「事故」**：演练是主动制造故障并验证恢复能力；事故是意料之外发生的。
  两者用同一个模板，但要在头部标注清楚。
- **记录不可用时长**：这是最能量化运维能力的数字（RTO）。

## 模板

复制下面这段开新的报告：

```markdown
# 演练/事故报告：<一句话标题>

| 项目 | 内容 |
|---|---|
| 日期 | YYYY-MM-DD HH:MM (时区) |
| 环境 | 集群/版本/规模 |
| 类型 | 计划内演练 / 意外事故 |
| 结果 | ✅ 成功 / ⚠️ 部分成功 / ❌ 失败 |
| 实测不可用时长 | N 秒/分钟 |
| 影响范围 | 谁受影响、影响多久 |

## 1. 目标 / 背景
为什么要做这件事（演练）/ 事情是怎么发生的（事故）

## 2. 前置侦察
动手之前查了什么，结论是什么

## 3. 操作步骤
可复现的完整命令

## 4. 验证证据
怎么证明「真的成了」—— 必须有可证伪的检查点

## 5. 发现的问题
包括过程中暴露的流程问题

## 6. Action Items
| 编号 | 改进项 | 优先级 | 状态 |

## 7. 可复用 SOP
浓缩成下次能直接照抄的命令块
```

## 计划中

| 演练 | 想验证什么 |
|---|---|
| 证书轮换 | `kubeadm certs renew` 全量续期 + 控制面重启，确认集群不挂 |
| 节点 NotReady | 停 kubelet 后，告警多久触发、Pod 多久被驱逐、恢复后能否自动回到 Ready |
| 上游不可达 | 让 CronJob 采集失败（改 DNS / 断网），验证 `RadarCollectFailed` 和 `RadarSnapshotStale` 告警 |
| etcd 数据目录直接删 | 比这次更极端的场景：数据目录整个没了（不是挪走），验证纯靠快照能否重建 |
| 镜像拉取失败 | 把 Deployment 镜像改成不存在的 tag，观察 `ImagePullBackOff` 与告警 |
| 磁盘写满 | 把 PVC 或系统盘写满，看 kubelet 驱逐行为和告警链 |
